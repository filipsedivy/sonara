# Agent API (CLI, IPC, MCP)

API version **1.1**; IPC protocol version **1**. This file is generated by
`cargo run -p sonara-agent --example gen_agent_docs` from the tool registry; edit the registry
(`crates/sonara-agent/src/contract/`), not this file.

Sonara exposes one set of tools through three transports. Every transport runs the same handler
code against the same project session (ADR 0005), so an agent sees and edits exactly what
the GUI shows, with one shared undo history.

| Transport | How |
|---|---|
| CLI | `sonara tools`, `sonara tool NAME '{"arg": 1}'`, `sonara batch steps.json` |
| Local IPC | newline-delimited JSON-RPC 2.0 to a running GUI or `sonara serve` |
| MCP (Claude Code) | `sonara mcp` (stdio), connecting to a running session or running headless |

## Using Sonara from Claude Code

```bash
# once, from any directory; the sonara CLI ships inside the app bundle:
claude mcp add sonara -- /Applications/Sonara.app/Contents/MacOS/sonara mcp
# or, from a checkout, after `cargo build --release -p sonara`:
claude mcp add sonara -- /path/to/sonara/target/release/sonara mcp
```

If a Sonara window (or `sonara serve`) is running, the MCP server attaches to it and the user
sees every edit live. Otherwise it hosts a headless session. Relative paths resolve against
the MCP server's working directory, which is also an allowed location.

Options: `--connect auto|always|never`, `--allow PATH` (repeatable), `--base-dir`,
`--audio auto|native|null`.

## Conventions

- **Time.** Positions are quarter-note **beats** from the song start, as numbers (`16` is bar 5 in
  4/4). They also accept `"bar:beat[:tick]"` strings (1-based, 960 ticks per beat) and seconds
  (`"12.5s"`). Lengths accept beats, `"4 bars"` / `"4b"`, or `"30s"`. Note starts inside a MIDI
  clip are beats relative to the clip start. Every reported position includes `beat`, `seconds`
  and `bar_beat`.
- **Units.** Levels are dB (fader −144…+12), pan is −1 (left)…+1 (right), tempo is BPM,
  frequencies are Hz, and times are in the unit given in each parameter's schema
  (`list_plugins plugin_id=...`).
- **Identifiers** are stable and opaque (`trk_…`, `clp_…`, `dev_…`, `snd_…`, `aut_…`, `med_…`,
  `n_…`; the master is `master`). Never rely on names or list positions.
- **Results** are envelopes: `{"ok": true, "tool": NAME, ...}`. Mutating tools return
  `committed`, `dry_run`, `project_version`, `operation`, `changes` (created, updated and deleted
  `{kind, id}` plus flags) and `result` (for example the new `track_id`).
- **Errors** are `{"ok": false, "error": {"code", "message", "details"}}`.
- **`dry_run: true`** on any mutating tool validates the call and reports what would change,
  without committing it.
- **Orchestration ids.** A note's `articulation` (`staccato`, `pizzicato`, `legato`) and the
  `instrument` of a `create_track` part (`violin`, `horn_f`) are ids of the orchestration
  vocabulary, matched exactly. A note without an articulation plays the instrument's ordinary
  sound; mute and vibrato ids (`con_sordino`, `non_vibrato`) hold over a passage and are refused
  on a note. An id that names nothing returns `INVALID_ARGUMENT` with the closest ids in
  `details.suggestions` and every accepted id in `details.available`. A part, which only an
  instrument track takes, is `{instrument, name, players, solo, player, notation: {transposition,
  clef}}`. The project stores a note's articulation with the note and a part with its track
  (project format version 2).

## Safety

- **File access** is restricted to allowed roots: the Sonara projects directory, the MCP
  server's base directory, the open project's folder and workspace, Settings → Agent access, and
  `SONARA_AGENT_ALLOWED_PATHS`. Symlinks are resolved before checking. Anything else returns
  `PERMISSION_DENIED`, with the allowed roots listed.
- **Two-phase confirmation** applies to destructive actions: discarding unsaved changes
  (`create_project`, `open_project`), deleting tracks that have content, and overwriting existing
  files (`save_project` to another path, exports with `overwrite`). The first call returns
  `CONFIRMATION_REQUIRED` with `details.confirmation_token`. Ask the user. If they agree, repeat
  the **identical** call with `confirmation_token`. Tokens are single-use, bound to the exact
  arguments, and expire after 10 minutes. The user can turn confirmations off in Settings.
- **Limits:** render length 3 h, preview length 15 min, 20 000 notes per call, 512 tracks, and
  16 concurrent background operations.
- **Long operations** (`render_preview`, `export_audio`, `export_stems`) run as background jobs.
  With `wait: true` (the default) the call blocks up to `timeout_seconds` and returns the result;
  otherwise poll `get_operation_status` and stop with `cancel_operation`.
- **Audit log:** every call is appended as JSONL to `<SONARA_HOME>/logs/agent-audit.jsonl`, with
  token-like values redacted.
- **No code execution:** the agent can only call tools. Nothing it sends is executed as code, and
  nothing reaches the real-time audio thread.

## Versions

The API version changes only by a deliberate, versioned decision. Version 1.0 is the first
published contract. A later 1.x version only adds: new tools, and new optional arguments or
optional fields of nested objects such as a note. Every tool, argument, default, description,
result and error code of 1.0 keeps its meaning, so a client written for 1.0 works unchanged.
`get_capabilities` and the IPC `hello` and `info` replies report the version.

1.1 adds to 1.0:

- the optional argument `part` of [`create_track`](#create_track)
- the optional field `articulation` of `NoteInput`, in [`create_midi_clip`](#create_midi_clip), [`add_midi_notes`](#add_midi_notes), [`edit_midi_notes`](#edit_midi_notes)

## IPC protocol

- **Discovery.** `<SONARA_HOME>/run/session-<pid>.json` (mode `0600`) contains
  `{pid, transport: unix|tcp, address, token, protocol, app, started}`. Stale files from dead
  processes are removed by clients.
- **Framing.** One JSON object per line, UTF-8, at most 32 MB per message.
- **Handshake.** The first request on a connection must be
  `{"jsonrpc":"2.0","id":1,"method":"hello","params":{"token":"…","protocol":1}}`. A wrong
  token gets error `-32001`; a protocol mismatch gets `-32002`. Either way the connection closes.
- **Methods:** `tools/list`, `tools/call {name, arguments}` (returns the envelope), `info`, `ping`.
- **Errors** use JSON-RPC error objects. Sonara errors carry `data: {code, message, details}`.
- **Timeouts.** Connecting times out after 5 s. Requests default to 3600 s; long work runs as
  jobs.

## A typical composition loop

1. `create_project` with name, BPM, time signature, `length: "64 bars"` and an optional template.
2. Add structure: `add_section` for intro, build, drop, breakdown and outro, and `add_marker`.
3. Add instruments: `create_track` with `instrument` + `preset` (see `list_plugins`).
4. Write material: `generate_midi` (chords, bass, arpeggio, drums, melody) or `create_midi_clip`
   with explicit notes. Then `duplicate_clip` / `edit_midi_notes` for variations.
5. Mix: `add_effect`, `configure_routing` (buses, sends, sidechain), `set_track_volume` / `pan`,
   `create_automation`.
6. `render_preview` with `per_track_levels: true`. Read `analysis` (LUFS, true peak, clipping,
   correlation, octave balance) and `issues`, then revise and render again.
7. `export_audio` (several formats in one call, optional loudness normalization), `export_midi`,
   `save_project`.
